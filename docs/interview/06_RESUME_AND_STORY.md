## 简历项目名

短视频对比诊断 Agent 系统（Java Spring Boot + Python LangGraph）

## 简历 Bullet 版本

1. **整体**：设计并实现短视频对比诊断 Agent 系统，输入目标视频和同题材参考视频，从开场钩子、结构节奏、价值传递三个维度输出带原文证据的改进建议。Java Spring Boot 负责任务、证据、结论的持久化和状态流转，Python LangGraph 负责单次诊断运行，docker-compose 一键部署。用户可以上传自己的评分标准 txt。一次约 1.5 分钟视频的对比（1 目标 + 1 参考 + 4 条自定义标准），从上传、预处理（转写 / OCR / 镜头检测）到出报告端到端约 2.7 分钟，其中诊断约 45 秒；单次模型成本约 ¥0.08（约 5.4 万 token），加转写合计约 ¥0.2。

2. **Java 可靠性**：后端以 MySQL 为事实源设计任务状态机，处理 agent-service 不可用、中途崩溃和回调异常三类故障：
   - 派发失败按 10s / 30s / 60s 退避重试，3 次后置为失败；
   - 运行超时（30 分钟）由定时扫描回收并重新派发，每次派发生成新的 agentRunId，旧 run 晚到的回调被拒绝；
   - 重复回调走 Redis 快速去重 + 数据库 (agentRunId, resultVersion) 唯一约束兜底；结论批量写入带幂等键。
   - 复查时发现并修复：`@Transactional` 同类自调用不生效（改为"抢占提交 → 事务外 HTTP → 失败回写"三段短事务）、Redis 去重标记早于事务提交（回滚后重发的回调会被误判重复，改为提交后标记）、并发建任务撞唯一索引返回 500；
   - 以 agentRunId 作为 traceId 贯穿 Java 派发、Python 三个并行专家和回调，一条命令即可查出整次诊断的跨服务日志。
   
   以上路径由 19 个集成测试（MockWebServer 模拟 agent-service）和状态机、去重、建任务单元测试覆盖（Java 共 34 个测试）。

3. **Agent harness**：参考 Strands Agents 设计实现 Agent harness，用 hook 事件 + 插件统一处理以下运行时治理，业务图与运行时治理解耦：
   - 轮次 / token / 步数 / 超时限额；
   - 并行分支取消；
   - 模型调用重试：区分可重试的限流和余额不足等账户级错误，后者立即终止整个运行；
   - 输出格式纠正和审计。

4. **编排与证据**：编排为 Supervisor → 3 个并行维度专家 → Evaluator（通过 / 定向打回 / 重新规划）→ Synthesizer。证据侧构建 2 分钟多模态时间轴：
   - ffmpeg 镜头检测 + 开场加密抽帧；
   - 并行 Tesseract OCR；
   - Whisper 分段转写。
   
   结论必须逐字引用口播 / 字幕原文，由系统核对原文真实存在；打回用尽仍违反硬规则的结论自动降级。

5. **评分标准检索（RAG）与自定义标准**：34 条通用评分点和品类私有规范以 md 文件维护，每个维度专家诊断前按"维度关注点 + 目标视频特征"检索 top-6 评分点交给模型，结论须注明依据，Evaluator 校验引用确实来自本次检索（引用率 168/168）。用户上传的标准由 LLM 拆分、归入维度并标注可检查范围（需要看画面 / 听音乐的标准如实判"无法判断"），逐条给出满足情况，未满足项排进改进优先级首位，冲突时以用户标准为准。消融实验：
   - 通用题（28 组 × 2 次）上开 / 关 RAG 命中 44/46 vs 43/46，误报均为 0/182，**准确率没有提升**；
   - 规则依赖题（21 组 × 2 次，另 2 组对照题标注有误未计入）上命中 28/28 vs 26/28、误报 2/32 vs 4/32。
   
   结论：RAG 的价值在模型不可能事先知道的私有规范和与直觉相反的边界规则，以及判定可追溯、改 md 即可改标准。

6. **质量评测与迭代**：设计规则判分的诊断质量评测集（26 组构造证据包、预埋 21 个已知问题，不用 LLM 打分），针对过度弃权、孤立挑毛病、自相矛盾迭代 4 轮质量规则。同一模型（deepseek-flash）、同一题集（26 组 × 2 次）上 v1 → v2：
   - 问题命中 32/42 → 41/42；
   - 误报 79/172 → 0/172（优势被当成问题 8/8 → 0/8）；
   - 带原文引用的结论 146/154 → 156/156，两次运行结论一致 126/156 → 155/156。
   
   基础题集（19 组 × 2 次）上 gpt-5.6-luna 命中 28/28、误报 0/108。

7. **难题集与模型选型**：基础题集被强模型做满后，补充 7 组难题（阈值边界、OCR 噪声、多参考分歧、节奏不均），由此发现并修复"节奏规则只看平均镜头时长"的缺陷。对比 OpenAI / DeepSeek 4 个模型的质量、成本与延迟后选定 deepseek-flash：难题集（7 组 × 3 次）命中 20/21、误报 0/96（修复节奏规则后），单价约为 deepseek-v4-pro 的 1/3~1/4，速度快 4~5 倍。

> 篇幅紧时保留 1、2、5、6。第 3、4 条可以合并成一条，第 7 条可以压成一句话。

### RAG 这条为什么又写回来了、怎么写

第二次修改时删掉它，是因为当时核对代码发现：检索只在带品类参数时触发，Java 从不传，**之前所有任务其实都没经过 RAG**。
之后做了改造（见 `docs/16` 第六、七轮）：每次诊断、每个维度都检索评分点，检索结果真正交给模型，结论必须注明依据并被校验。

写法上的原则：**不说 RAG 提升了准确率**。消融显示通用判断上开关持平，这一点主动写出来；
它的定位是"让判定按规则走 + 可追溯 + 可维护"，证据是规则依赖题组（尤其是私有规范和反直觉边界规则）。
"检索同类爆款参考案例"仍然不写：参考视频是用户上传的，系统不检索它们。

## 30 秒介绍

我做了一个短视频对比诊断 Agent：给一个目标视频和同题材的参考视频，系统从开场钩子、结构节奏、价值传递三个维度做对比，给出带原文证据的改进建议。工程上 Java 是事实源，负责任务状态机、失败重试、超时回收和回调幂等；Python 只管单次诊断，外面包了一层参考 Strands 设计的 harness。评分标准放在知识库里，每次诊断都检索，用户也可以上传自己的标准。我花精力最多的是诊断质量：自己搭了一套规则判分的评测集，迭代了四轮规则，在同一个模型、同一套题上把命中率从 76% 提到 98%，误报从 46% 降到 0。

## 2 分钟项目讲述

短视频诊断很容易做成"把视频描述丢给模型自由发挥"的 demo，但那样结论没法追溯，也没法评估好坏。所以我做了三件事。

**第一是可靠性。** Java 是业务事实源。诊断是异步的，所以重点处理了三类故障：
- agent-service 连不上：派发按 10 秒、30 秒、60 秒退避重试，3 次后失败；
- 跑到一半挂了：30 分钟超时由定时任务回收、重新派发。每次派发生成新的 agentRunId，旧 run 晚到的回调直接拒绝；
- 回调重复到达：先用 Redis 快速去重，再靠数据库的唯一约束兜底。

这些路径都有集成测试，用 MockWebServer 模拟 agent-service。后来我按并发、幂等、事务的清单复查了一遍，又发现几个真问题：`@Transactional` 是同类调用、根本没生效；Redis 的去重标记在事务提交前就写了，回滚后重发的回调会被当成重复丢掉。都修了并补了回归测试，顺便用 agentRunId 把 Java 和 Python 的日志串成一条链路。Python 侧我参考 Strands Agents 做了 harness，限额、取消、重试、审计都是插件。有一次 OpenAI 余额用完，429 被当成限流重试，专家失败后弃权，任务却显示成功。后来我把账户级错误单独识别出来，直接终止运行。

**第二是证据。** 一开始只分析前 15 秒，基本说不出东西。我把窗口扩到 2 分钟，用 ffmpeg 做镜头检测和抽帧、Tesseract 做 OCR、Whisper 做分段转写，合成一条带时间戳的证据时间轴。模型看不到画面，所以每条结论必须逐字引用口播或字幕原文，系统会去核对。

**第三是质量评测。** 第一次跑真实视频，结论类型全是 unknown，还出现自相矛盾。我搭了一个 mock 评测集：证据包里预埋已知问题，按规则判分。迭代了四轮：
1. 解决过度弃权；
2. 发现模型其实是孤立地给目标挑毛病，没有和参考比较。改成让模型分别给目标和参考打分，由分数决定结论方向；
3. 发现打回用尽后违规结论照样放行，于是加了硬规则和强制降级。

之后强模型在基础题上满分，我又补了 7 组难题，用它发现了一个规则缺陷，最后按质量、成本、延迟选了 deepseek-flash。

**最后是评分标准。** 我把评分点做成 md 知识库，每次诊断都检索，结论要注明依据；用户也能上传自己的标准。做了消融：通用题上开不开 RAG 结果差不多，模型本来就懂；差别出在私有规范和反直觉的边界规则上。所以我对它的定位是让判定按规则走、可追溯，而不是提准确率。

## STAR 故事 1：诊断质量四轮迭代（最推荐讲）

**Situation**：第一次真实运行，结论类型全是 unknown；开场专家说"没有价值承诺"，价值专家说"第 3 秒就传达了收益"；目标比参考好的地方也被标成 P0 问题。

**Task**：先把"诊断好不好"量化，再有依据地改。

**Action**：搭 mock 评测集。构造与 Java 证据接口同格式的证据包，预埋已知问题，按"维度 + 问题类型"规则判分，避免让模型自己判卷。每轮先逐条看失败样本找根因再改：
- 第 1 轮：引入分类表、结论方向、原文引用校验、跨维度矛盾检测；
- 第 2 轮：漏报主要来自过度弃权。示例里的 confidence 0.0 被模型照抄，打回提示里又写着"改为弃权"；
- 第 3 轮：模型没有真正和参考比较。改为分别打分、由分数决定方向；
- 第 4 轮：打回用尽后违规结论照样放行。加硬规则和强制降级。

**Result**：
- 每轮的真实数据都在报告里：
  - 第 1 轮基线：15 组 × 1 次，v1 命中 7/12、误报 20/40、原文引用 6/42；
  - 第 4 轮：19 组 × 2 次，命中 26/28、误报 5/108、原文引用 110/114。
- 因为题集在迭代中扩充过，简历上用的是同一题集重跑的 v1 / v2 对比（报告 `quality-20261029-205222`，deepseek-flash，26 组 × 2 次，RAG 开）：命中 32/42 → 41/42，误报 79/172 → 0/172，原文引用 146/154 → 156/156，一致性 126/156 → 155/156，每样本 token 3.8 万 → 3.1 万，耗时 35 秒 → 21 秒。
- 被追问时说明：v1 没有分类表，命中 / 误报按"维度 + 关键词"匹配，判分口径比 v2 宽松；v2 唯一一次漏报是 c11 的第 2 次运行。
- 强模型 gpt-5.6-luna 在 19 组 × 2 次上命中 28/28、误报 0/108，平均打回次数从 1.97 降到 0.13，每个样本的 token 从 4.3 万降到 2.5 万。

## STAR 故事 2：Java 侧故障恢复（被问后端深度时用）

**Situation**：诊断是异步长任务。agent-service 可能连不上、可能跑到一半崩溃；回调可能重复到达，也可能是重试之后旧 run 才回来。

**Task**：保证任务状态不被重复回调或过期回调污染，失败可以自动恢复，并且有上限。

**Action**：
- MySQL 是唯一事实源，任务状态机拒绝非法流转（比如已完成的任务不能再被置为失败）；
- 派发：定时扫描每 5 秒捞取待派发和待重试的任务，失败按 10s / 30s / 60s 退避重试，3 次后失败；
- 超时：派发时写入超时时间（30 分钟），定时扫描每 30 秒回收超时任务，置为重试；
- 每次派发生成新的 agentRunId。回调必须带回 agentRunId 和单调递增的 resultVersion，`canAcceptAgentResult` 会检查状态、超时、run 是否为当前 run、版本是否更新；
- 重复回调：Redis 快速判重，数据库 (agent_run_id, result_version) 唯一约束兜底；结论批量写入带 idempotencyKey 唯一约束；
- 任务实体用 JPA `@Version` 乐观锁。
- 复查（按并发 / 幂等 / 事务 / 可观测性清单）后修复：
  - `@Transactional` 同类自调用不生效 → 派发拆成"抢占并提交 → 事务外发 HTTP → 失败才回写"，避免把 HTTP 包进长事务；
  - 抢占失败（被别的实例抢走）原来会走进失败分支、把别人的任务改成重试 → 改为跳过；HTTP 失败但回调已先完成任务时不再回写；
  - Redis 去重标记早于事务提交 → 改为 `afterCommit` 标记；本机兜底集合加过期和上限；
  - 并发建任务撞唯一索引返回 500 → 回查返回已存在的任务；
  - traceId：MDC + `X-Trace-Id`，派发链路 traceId = agentRunId，Python 侧 ContextVar 显式带进专家线程池。

**Result**：19 个集成测试 + 状态机 / 去重 / 建任务单元测试（Java 共 34 个测试）覆盖以下场景：
- 派发失败重试；
- 达到上限后失败；
- 超时回收；
- 重复回调幂等；
- 过期 run 回调被拒绝；
- 批量结论幂等；
- 路径与 body 中 jobId 不一致时拒绝；
- 内部接口鉴权；
- 抢占冲突跳过、回调先于 HTTP 失败到达、超时扫描遇到已完成任务；
- Redis 标记提交后才生效、回滚不生效；
- 并发重复建任务返回同一个任务；
- traceId 透传与非法值替换。

真实任务验证过：一条 `Select-String <agentRunId>` 拿到 Java 派发 → Python 三专家并行 → 写回结果的完整跨服务日志。

**边界**（被追问时主动说）：
- 没有 worker 租约 / `SKIP LOCKED`，多实例时靠乐观锁抢占（输的一方跳过）+ 回调幂等兜底；
- 没有用 MQ / Outbox，派发是数据库轮询。

如果要上多实例，下一步是加 `SELECT ... FOR UPDATE SKIP LOCKED` 或租约字段。

## STAR 故事 3：用难题发现规则缺陷 + 模型选型

**Situation**：强模型在 19 组基础题上满分，题集失去区分度；真实视频里还出现过"平均镜头时长接近、实际节奏差很多"却被规则拦下的情况。

**Task**：既要能区分模型，又要验证规则在新话题上是否成立。

**Action**：
- 补 7 组难题，话题全部换新；
- 逐条复盘失败原因：
  - 有的是我出题有歧义，就修题，不改规则去迁就模型；
  - 有的是规则缺陷：节奏规则只看平均镜头时长，模型正确指出了"中位 1.2 秒、最长 39.6 秒"仍被降级。于是改成平均、中位、最长镜头、碎镜头数都接近才算节奏相同，并确认前 19 组的判定不变；
- 对比 4 个模型。

**Result**：
- 在难题集上：
  - deepseek-flash 第一次跑命中 67%，修题 + 修节奏规则后命中 20/21、误报 0/96；
  - deepseek-v4-pro 命中 13/21，误报 0，每样本耗时 130 秒 vs 28 秒，单价是 flash 的 3~4 倍；
  - 选定 flash。
- 还暴露出"每个维度只能输出一条结论"的架构限制，列为下一步。

## STAR 故事 3.5：RAG 消融（被问"RAG 有什么用"时用）

**Situation**：评分点检索接入主流程后，需要证明它到底有没有用，而不是默认它有用。

**Action**：
- 2×2 消融（提示词写死定义 / 不写 × RAG 开 / 关），28 组 × 2 次；
- 发现通用题测不出差别后，专门出了 23 道"答案依赖某条评分点"的题：通用评分点里的边界规则、知识教程类私有规范、不带品类的对照题；每题标注依赖哪条评分点，并统计是否被检索到、被引用。

**Result**：
- 通用题上开关持平（44/46 vs 43/46，误报均 0/182），我在文档和简历里都直接写了"准确率没有提升"；
- 规则依赖题上 28/28 vs 26/28，误报 2/32 vs 4/32；最清楚的两个例子：
  - "长镜头 + 密集字幕不算拖沓"：关 RAG 两次都误报，开了 0 次；
  - "教程类开场不许反问"：关 RAG 时模型也看出开场有问题，但按自己的理解归类；开了才按私有规范归类。
- 还复盘出两个题目设计问题：两道对照题是我标错了（目标确实比参考差）；私有规范题里参考视频本身就示范了规则，模型对比就能答对。更干净的做法是出"反向题"（参考按直觉做得好但违反私有规范），列为下一步。

## STAR 故事 4：Agent harness 重构

**Situation**：限额、重试、超时、审计散落在各个节点里；三个专家并行，一个超限，其它分支还在跑。

**Action**：参考 Strands Agents，定义模型调用前后、工具调用前后等 hook 事件，限额、取消、重试、输出格式纠正、审计都做成插件：
- 停止信号用 BaseException 子类，业务代码的 `except Exception` 拦不住它；
- 一处超限，所有并行分支在下一个检查点退出；
- ContextVar 绑定当前运行，线程池里也能拿到。

**Result**：服务、演示、评测三处共用同一套 harness。后来加"余额不足立即终止"，只改了一个插件。

## STAR 故事 5：部署排障（问"遇到过什么坑"时用）

- **Data too long**：Hibernate 6 在 MySQL 上把没写长度的 `@Lob String` 映射成 `tinytext`，证据 JSON 一长就报 Data too long。统一改为 `columnDefinition = "LONGTEXT"`。
- **Agent 拿到的证据为空**：预处理阶段的特征以占位 jobId 保存，按任务查不到。改为按任务查不到时按视频资产查。
- **定时任务配置失效**：Spring 6.1 的 `@Scheduled(fixedDelayString)` 要写 `PT5S`；全局异常处理吞掉了异常，先补日志才定位到问题。

## 被问到 RAG 时怎么答

检索的是**评分标准**，不是参考视频：34 条通用评分点（判定重点 + 边界），加上品类私有规范，都是 md 文件，改文件就改判定。
每个维度专家下结论前，用"维度关注点 + 这条视频的特征"（开场有没有收益词、有没有自我介绍、镜头是否长期不变、结尾有没有行动号召……）检索 top-6，
私有规范按品类全部带上；结论必须注明依据了哪几条，Evaluator 校验引用确实来自本次检索。检索器本身做过评测：60 条人工审核查询上混合检索 Recall@5 = 0.90（held-out 18/20）。

它有什么用，我做了消融，结论要说全：
- 通用判断上开关持平，模型本来就懂，而且有参考视频可以对比，所以**不提准确率**；
- 有用的是两类：模型事先不可能知道的私有 / 用户规范，和与直觉相反的边界规则（规则依赖题组 28/28 vs 26/28，误报 2/32 vs 4/32）；
- 附带价值：每条结论可追溯到评分点，标准可维护。

追问"题目会不会有偏"：会。系统是对比诊断，参考视频按规则做了的话模型对比就能答对，所以部分私有规范题测不出差别；更干净的是"反向题"，还没做。

## 面试中的诚实边界

可以强调：

- 端到端闭环：上传 → 预处理 → 多模态证据 → Agent 诊断 → 回调落库，docker-compose 一键部署。
- 测试：Python 228 个，Java 34 个（19 个集成测试 + 15 个单元测试）。
- Java 和 Python 日志用 agentRunId 串成一条链路，真实任务验证过。
- 评测报告可复现，失败样本都复盘过，修过自己出错的题。

必须主动说明：

- 质量评测集是自己构造的 mock 证据包，按规则判分。它测的是诊断逻辑，测不了 OCR / ASR / 镜头检测的质量，也不代表真实视频上的准确率。下一步是做人工标注的真实视频集。
- luna 的满分是在基础题集上；换模型带来的提升不算规则的功劳。
- 每个维度只输出一条结论，一个维度有多个问题时会漏。
- 后端没有 worker 租约、MQ、Outbox、熔断限流、指标告警；没有用户体系，公开接口没做越权校验。
- RAG 在通用判断上没有提升准确率（消融结果）；规则依赖题组是自己出的，部分题目对比参考就能答对。

不要夸大：

- 不说生产级高并发、线上 SLA、分布式事务。
- 不说 JPA `@Version` 是 CAS。
- 不说模型"看懂了视频画面"，它看到的是 OCR / ASR / 镜头统计组成的文字时间轴。
- 不说 RAG 提升了诊断准确率；它的作用是让判定按规则走、可追溯。

|---|---|

- 模型：4 次调用，54,065 token（输入 38,220 / 输出 15,845）；DeepSeek 账单该小时 ¥0.17 对应两次任务（另一次 50,626 token），单次约 ¥0.08，与当天均价（¥8.22 / 607 万 token）推算一致；

- 想写"3 次中位数"可以按下面的方法再跑两次。

测法（PowerShell，在放视频和 criteria.txt 的文件夹里运行，中途不要 Ctrl+C）：

```powershell
$target = "target.mp4"; $reference = "reference.mp4"
$t0 = Get-Date
$tv = (curl.exe -s -F "file=@$target" -F role=target http://localhost:8080/api/v1/videos/upload | ConvertFrom-Json).data.videoId
$t1 = Get-Date
$rv = (curl.exe -s -F "file=@$reference" -F role=reference http://localhost:8080/api/v1/videos/upload | ConvertFrom-Json).data.videoId
$t2 = Get-Date
$job = (curl.exe -s -F targetVideoId=$tv -F referenceVideoIds=$rv -F "criteria=@criteria.txt" -F "targetTitle=e2e $(Get-Date -Format HHmmss)" http://localhost:8080/api/v1/analysis/jobs/with-criteria | ConvertFrom-Json).data.jobId
do { Start-Sleep 2; $s = (Invoke-RestMethod http://localhost:8080/api/v1/analysis/jobs/$job).data.status; Write-Host -NoNewline "$s " } while ($s -notin 'COMPLETED','FAILED')
$t3 = Get-Date
"目标 {0:N1}s / 参考 {1:N1}s / 诊断 {2:N1}s / 合计 {3:N1}s" -f ($t1-$t0).TotalSeconds, ($t2-$t1).TotalSeconds, ($t3-$t2).TotalSeconds, ($t3-$t0).TotalSeconds
docker compose logs agent-service --since 15m | Select-String "agent_job_success" | Select-Object -Last 1
```

成本 = DeepSeek 控制台"用量信息"按小时的扣费（或 token × 单价）+ 转写分钟数 × 转写单价。
